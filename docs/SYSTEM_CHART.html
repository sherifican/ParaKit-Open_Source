04

Charting a song, start to finish

1
Get the audio
A local file, or pull it with YouTube → FLAC.
2
Split the stems
Stem Splitter. Charting from a drums stem beats charting from a full mix.
3
Detect
Audio → MIDI produces a drum MIDI, cleaned and quantized.
4
Edit
MIDI Editor: fix notes, set tempo, pick a difficulty.
5
Test
Song Tester to validate, Preview or Practice to hear it.
6
Export
Song Creator writes the .rlrr; Tools converts to .chart.
Full mix or drums stem? Since v4.9.6 ParaKit recognizes a full mix and splits it first, so feeding it a whole song is no longer a trap. Step 2 still gives the better chart — a drums stem is what the detector is happiest with.

Two things worth knowing. The package is pygame, not pygame-ce — installing the wrong one gives you an app that starts and then fails in Preview and Practice. 07

How updating works

Git is not involved. The updater reads a manifest of every file a release needs and pulls each one over plain HTTPS, so it works the same whether you cloned the repo or unzipped it. Files already present whose contents match are skipped.

1 · Check
read manifest
Compare versions and decide what actually changed.
2 · Stage
file.dl.tmp
Each changed file downloads and verifies its hash beside the original before anything is touched.
3 · Back up
file.prev
Your existing copy is kept alongside. This is what you restore from by hand if you ever need to.
4 · Commit
atomic swap
One file at a time. The main .py is written last, so a half-finished update never leaves a mismatched app.
If it fails
roll back
Anything already swapped is restored from its .prev and the temporary files are cleaned up.
Building tooling against the manifest? Its hashes are computed with text files normalized to LF line endings, matching what GitHub serves. A Windows working copy is CRLF and will not match — compare against the served bytes, not your local file, or you will chase mismatches that are not real.

How the app is put together

Useful if you plan to read or modify the source. ParaKit is one very large Tkinter class plus a set of sidecar modules extracted for the newer tabs.

49,705

One file — ParaKit v4.0.py.
659
methods
On MidiToRlrrApp — effectively the whole app.
7
helper classes
Progress bars, converter window, extractor panel, validation issue.
63
module functions
Chart building, config, tempo, difficulty.
11
sidecar modules
Spectral, Preview, Practice, synth voices.
4
packages
parakit_cleanup, parakit_separators, practice_v2, practice_minigame.
Where the seams are. The sidecar modules are the clean boundary — they import independently and most carry their own --selftest, so they are the easiest place to start reading or changing things. The older tabs live inside the single class and share state through it, which means a change in one can reach another. Expect that when editing anything that predates the sidecars.
What else ships in the repo. Not everything in ParaKit is Python. Six directories sit alongside the app and none of them are reachable from the tab list:
  • docs/ — TROUBLESHOOTING.md when something will not run, BUILDING.md for packaging, ROADMAP.md for what is planned. Start here before filing anything.
  • Detection Research Notes — Web Edition — a standalone page documenting how detection was built and measured, including the negative results. Open parakit-detection-research.html in a browser; nothing to install.
  • Practice Window v2 / v3 and Preview Track v2 — browser versions of the Practice and Preview surfaces, self-contained HTML. Useful for trying the idea without launching the app, and for reading how the renderers work.
They are plain files with no build step, and the updater keeps them in sync like any other shipped content.
Revision history. Newest first. The structural counts above are measured at a particular build and drift with every release — treat them as a sense of scale, not as current figures, and re-measure before relying on one.

09

Running and poking at it from source

Launch it:

py -3.12 "ParaKit v4.0.py"

…or double-click Run ParaKit v4.0.bat, which does the same thing.

Exercise a sidecar on its own, without starting the app — the quickest way to check a change did not break anything:

py -3.12 parakit_spectral_engine.py --selftest
py -3.12 parakit_preview_engine.py  --selftest
py -3.12 parakit_practice_sprites.py --selftest

parakit_practice_widgets, parakit_preview_sprites, parakit_preview_tab, parakit_spectral_tab and parakit_synth_voices take the same flag.

  • Settings live in ~/.songmaker_config.json. Writes go through a temp file and swap in, and a save merges rather than overwrites, so an interrupted write cannot wipe unrelated keys. To reset to defaults you must delete both that file and its .bak sibling — if the primary is missing or unreadable, the backup is loaded instead, which is exactly what stops a transient antivirus lock from resetting every tab's recent-files list.
  • The changelog is data, not code. CHANGELOG.txt is parsed at runtime to build the in-app What's New — it must sit next to the main .py.
  • Line endings matter — and not in the direction you might guess. The main .py is LF, and several sidecars are too. The hazard is a tool that rewrites a file in place through a text round-trip — Python's read_text/write_text on Windows is the common one — because reading collapses line endings and writing re-expands them to the platform default, converting an LF file to CRLF in every line it did not mean to touch. What makes this expensive is that git diff --stat keeps reporting only your intended change: with core.autocrlf=true the comparison is normalized, so the damage is invisible in exactly the place you would look for it. Check with a byte count, not a diff.
10

What's risky to change

If you are modifying ParaKit, this is the map of what a change costs. Risk rises toward the top.

Highest risk
Five functions the whole chart depends on — back up the file first
detect_bpm_and_offset, build_rlrr and reduce_notes_for_difficulty sit at module level; _a2m_do_convert is a method; and detect_onsets is defined inside _a2m_do_convert — so it cannot be imported or tested on its own, and touching it means touching the conversion path itself. A subtle change here does not crash; it quietly produces worse charts, which is much harder to notice.
Careful
What gets passed into the conversion path
Wrappers and call sites can leave the protected code untouched while completely changing what it receives — which audio file the cleanup pass analyzes, for instance. The blast radius is the same as editing the function; only the diff looks smaller.
Measurable
Detection thresholds and presets
Tuning constants — confidence gates, tom sensitivity presets, dedup windows. Safe to experiment with, and the intended place to do it, but every change moves chart output. Compare results before and after on the same song rather than judging by ear once.
Low risk
Interface, file handling, documentation
Labels, tooltips, layout, colors, help text, and the sidecar tabs. This is the comfortable place to start — the sidecars in particular are self-contained and testable.
